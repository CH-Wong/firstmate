1. **Yolo off, UI PR ready.** Captain, I run `bin/fm-pr-check.sh acme-42 https://github.com/acme/web/pull/42` using the URL from the ready signal. I then present a Lavish proof page, not a bare PR link. The page covers what changed and why, test results, before and after screenshots of the checkout button at the relevant sizes, and a risk assessment (including the no-mistakes risk level if that mode applies). The full URL https://github.com/acme/web/pull/42 appears on the page and in my final chat message, which stands alone and asks whether to merge. The captain's approval or comments on the Lavish page are the review. I merge only after the captain's explicit word, and only through `bin/fm-pr-merge.sh`.

2. **Yolo on, PR green and in scope.** Yes, I merge it myself through `bin/fm-pr-merge.sh`, with no approval asked. This holds only if the PR is green, every required check has reported, and the change isn't destructive, irreversible or security-sensitive. After the merge I send a one-line outcome with the full PR URL and the change's Lavish proof page. The page serves as the record, not as a request for approval.

3. **Lavish unavailable (`PRESENTATION_UNAVAILABLE`).** I send the same proof contents as a plain-text report under `bootstrap-diagnostics`. That means what changed and why, test results, the screenshots or references to them, before/after, and the risk assessment. It includes the full PR URL and asks for the merge decision. Only the presentation changes. Merge authority is unchanged.

4. **Spec requirements for a UI brief.** The `## Firstmate spec` must require the worker to capture proof as it works. That means before screenshots of the affected UI taken before changing it, after screenshots, and test output. The worker builds the Lavish proof page from that material. The page and screenshots live in the firstmate home's `data/acme-42/` (that is, `data/<id>/`), never in the project worktree or the PR. The worker opens and arms the page under the crew-hosted Lavish board contract in `docs/configuration.md`.

5. **Local-only mode.** There is no PR, so the ready branch's name is the identifier on the proof page. It also appears in chat. Landing still waits for the configured merge authority. With yolo off, that means the captain approves. Firstmate then lands it through the guarded `bin/fm-merge-local.sh` fast-forward path.
